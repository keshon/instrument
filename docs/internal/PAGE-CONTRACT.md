# Контракт страницы

Два вида страницы под контрактом, и различие не косметическое:

| `layout:` | Что это | Особенность |
|---|---|---|
| `component` | Компонент: его **выбирают** среди альтернатив | «Когда использовать» отвечает на «а не взять ли другое» |
| `foundation` | Основание: цвет, пространство, движение. Его не выбирают — это материал | Есть раздел «Шкала»: перечисление значений целиком |

Обязательный набор у обоих один: `usage`, `a11y`, `api`, `related` и главный
пример. Каталоги `about` и `internal` вне контракта — там проза о проекте, а не
описание поверхности.


**Живой документ**, в отличие от соседей по каталогу: он описывает не решение,
принятое однажды, а правило, которое проверяет сборка. Расходиться с
`site/internal/content/sections.go` он не имеет права — там словарь, здесь
объяснение.

---

## Зачем

До контракта страница была потоком прозы с произвольными подзаголовками. На
сорока семи компонентах это дало сто двадцать разных H2, из которых
повторялись четыре. Остальные девяносто встречались ровно по одному разу:
«Каретка», «Пульсация, а не блик», «Оговорённое исключение».

Следствий было три, и все видны читателю:

- **оглавление работало шумом.** На странице таблицы оно перечисляло
  двенадцать заголовков, из которых узнаваемы два;
- **страницы не сравнивались.** Найти доступность у бейджа и у меню значило
  прочитать обе страницы целиком;
- **якорь ломался при смене языка.** `#варианты` в русской версии и
  `#variants` в английской — это две разные ссылки на один раздел.

## Как устроено

Секция задаётся **обычным H2**, текст которого стоит в словаре. Ни директив,
ни списка секций во frontmatter: список был бы вторым источником истины и
разошёлся бы с телом на первой правке, а директивы сделали бы `.md`
нечитаемым на GitHub.

```md
## Варианты      →  id=variants, порядок 50, EN «Variants»
## Придумал сам  →  ошибка сборки на странице с layout: component
```

Что даёт словарь:

| | |
|---|---|
| устойчивый якорь | `#variants` в обеих языковых версиях |
| перевод заголовка | EN-версия непереведённой страницы уже имеет английский каркас |
| порядок чтения | «Доступность» выше «Вариантов» — ошибка, а не мнение автора |
| единое имя | «Справочник» и «API» — один раздел, и печатается он одинаково |

## Разделы

Порядок обязателен, состав — нет. У кнопки разделов тринадцать, у спиннера
семь, у модалки свои — с «Устройством» и «Поведением». Раздел «Когда не
использовать» из одной фразы, написанный потому, что шаблон велел, хуже его
отсутствия.

| Порядок | id | Заголовок | Про что |
|---|---|---|---|
| 10 | `install` | Установка | Только если подключение нетривиально |
| 20 | `usage` | Использование | Минимальный рабочий пример |
| 30 | `when` | Когда использовать | И что взять вместо |
| 40 | `anatomy` | Устройство | Части. Только у составных |
| 45 | `scale` | Шкала | Перечисление значений. Только у **оснований** |
| 50 | `variants` | Варианты | Семантические и визуальные |
| 60 | `sizes` | Размеры | Размеры и плотность |
| 70 | `states` | Состояния | И переходы между ними |
| 80 | `icons` | С иконкой | Иконка, icon-only, размещение |
| 90 | `behavior` | Поведение | Что делает платформа, что кит, что приложение |
| 95 | `js` | JS | Что вызвать: методы, события, опции-атрибуты |
| 100 | `composition` | Композиции | С какими компонентами собирается |
| 110 | `patterns` | Сценарии | Законченные экраны |
| 120 | `rules` | Правила | Пары «так / не так» |
| 130 | `a11y` | Доступность | Клавиатура, ARIA, контраст, цель, движение |
| 140 | `customization` | Настройка | Переменные, токены, свой вариант |
| 150 | `api` | API | Полная техническая поверхность |
| 160 | `related` | Связанное | Что смотреть дальше |

Раздел `js` отделён от `behavior` намеренно: «Поведение» отвечает на «что
происходит», `js` — на «что для этого вызвать». Внутри он устроен по
Bootstrap: *что делает кит · Методы · События · Опции*, и порядок этот
неслучаен — сначала выясняют, надо ли вообще что-то писать.

**Объявил `needs-js` — покажи вызов.** Страница с пометкой в шапке обязана
содержать хотя бы один блок кода на JS. Пометка без кода — обещание того же
рода, что необъявленная роль: она сообщает «нужен скрипт» и оставляет
читателя гадать какой.

**Обязательны четыре:** `usage`, `a11y`, `api`, `related` — и главный пример.

## Главный пример

Первый живой пример стоит **до первого H2**, сразу за определением. Он не
документирует, он показывает характер компонента: тот, кто пришёл со страницы
другого кита, должен за секунду понять, на что смотрит.

```md
Действие, которое пользователь запускает сам.

```html preview
<button class="inst-btn inst-btn--primary" type="button">Запустить</button>
```
```

## Семантические блоки

Правило дизайн-системы — данные, а не проза: у него есть знак, и читают его
сравнением. Обычным Markdown это не выражается.

```md
:::do Одно primary на экран
Главное действие ровно одно.
:::

:::dont Кнопка вместо ссылки
Переход по адресу — это `<a>`.
:::
```

Идущие подряд правила встают в один ряд по два. Кроме `do` и `dont` есть
`note`, `warn`, `danger`, `ok` — они разворачиваются в китовый `inst-note` с
соответствующим тоном.

## Перенос страницы

1. `layout: component` во frontmatter — это и есть объявление контракта;
2. заголовки — из словаря. Всё остальное опускается на H3 внутрь раздела;
3. «Справочник» → «API», «Разметка» → «Использование», «Части» → «Устройство»;
4. правила — в `:::do` / `:::dont`, врезки `>` — в `:::warn`;
5. разделители `·` между ссылками в «Связанном» убрать: их работу делает
   промежуток;
6. `go run ./cmd/site` из `site/`. Ошибки контракта роняют сборку.

Что мешает переносу остальных страниц, показывает

```sh
go run ./cmd/site -contract
```

Эти замечания сборку **не** роняют: волна без своего критерия готовности не
засчитывается, но и не блокирует соседние.

## Почему на странице нет раздела «почему так»

Первая версия шаблона его содержала: туда переезжали `.why` из живой
спецификации. Переезжать оказалось нечему — весь этот текст уже стоял в
`about/design-principles.md` дословно, то есть страница заводила второй
источник истины для прозы. Прозаические дубликаты расходятся быстрее кодовых:
их ничто не проверяет.

Тест для каждой такой записи: **меняет ли она то, что читатель напечатает?**

| Меняет | Куда идёт |
|---|---|
| «Заливка под белой подписью не светлее 0.56» | В таблицу CSS-переменных — туда, где её прочтут в момент переопределения |
| «Наведение меняет только `--btn-bg`» | Туда же: это причина, по которой вариант — две строки |
| «У тона два передних плана» | В токены |

| Не меняет | Куда идёт |
|---|---|
| «Раньше базовое правило писало `background` напрямую» | Никуда. Это история git |
| «Нажатие — `scale(0.985)`, а не `0.95`» | Остаётся в `about/design-principles.md` |
| «Шов — снятая рамка, а не отрицательное поле» | Туда же: деталь реализации |

Из двадцати одной записи первой версии тест прошли три. Остальные либо уже были
сказаны выше на той же странице, либо являются археологией.

## Дисциплина стилей сайта

Отдельное правило, появившееся по факту нарушения: в `docs.css` оказались
`text-transform: uppercase` и ссылка на несуществующий `--tracking-wide`.
Второе браузер молча отбросил, первое осталось — и получился ровно тот
«заголовок капсом с трекингом», который третий принцип конституции называет
неправым дословно.

Теперь `check.Assets` роняет сборку, если в `docs.css` или `demo.css`:

- используется `var(--x)`, которого в ките нет;
- встречается `text-transform` — во всём ките его ноль раз;
- стоит цвет шестнадцатеричным литералом.

Комментарии и `data:`-URI из проверки исключены: в первых нарушения законно
приводятся как примеры, во вторых цвет служебный — маска красится
`currentColor`.

Собственных переменных у сайта две — `--c` и `--v` в `demo.css`, оба канал
ДАННЫХ для показа токенов. Список закрыт: третья должна потребовать правки
`ownVars` и объяснения, зачем она.
