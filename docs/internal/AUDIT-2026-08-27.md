# Audit 2026-08-27 — six Claude Code screens rebuilt from the kit

Six screenshots of Claude Code were rebuilt out of existing classes, then the
reference and the rebuild were measured against each other.

## Method, and what it is worth

The numbers below were read **off screenshots**, not off a live DOM. That is
weaker than `AUDIT-2026-08-22.md` and is said here so nobody mistakes one for
the other. Three things make them usable anyway:

- The captures were taken on Windows at 150%, so every image is at a device
  pixel ratio of **1.5**. The factor was not assumed: one screenshot contains
  Claude Code's own chrome **and** a kit page inside its browser pane, and two
  kit elements of known CSS height — `--control-h-sm` at 24 and
  `.inst-input--sm` at 24 — both measure 36 image px. 36 ÷ 24 = 1.5, twice.
- Edges were taken from pixel runs on a canvas, not by eye. A fill is read as
  an exact RGB triple and its extent counted; a border is a run of length 1.
- Claude Code honours the OS scale factor rather than upscaling a bitmap: its
  1px borders land as clean solid single pixels (`rgb(230,230,230)`), and the
  kit's `--hairline: 0.5px` resolves to exactly one device pixel. A stretched
  bitmap would smear both.

Radii are the exception and are given as approximate: a corner's first-row
inset is inflated by antialiasing, so the solver reads high. Heights, widths,
fills and borders are exact.

Nothing in `src/` was changed while measuring.

This is the headline and it is the opposite of what the rebuild looked like.

| Address field | **24** | **24** | equal |

Menu row pitch was taken from the account menu: eleven text bands at 35–37

**The kit is not geometrically bigger. It is typographically heavier.**

## Where the bulk actually is

| | Reference | Kit | Ratio |
|---|---|---|---|
| Metric tile | 110 × **44.7** | ~163 × **80.4** | **1.80** |
| — its label | 12px | 14px | 1.17 |
| — its value | ~13px, semibold | **28px**, semibold | **2.15** |
| — its padding | ~8 | 12 | 1.5 |
| — gap between tiles | 5.3 | 12 | 2.26 |
| Two-row browser chrome | 67.3 | 81.4 | 1.21 |

The metric is the whole story. In the reference a metric is a **labelled
fact** — the value is barely larger than its label and is told apart by weight
and colour. In the kit it is a **big number**: value at twice the label.

### The kit's own rule already forbids it

`--text-2xl` has exactly two users: `h1` in `base.css:51` and
`.inst-metric-value` in `surfaces.css:258`. `.inst-page-title` is `--text-xl`.

So a number in a tile is set **28px against a page title of 22** — the loudest
type on a screen is a metric rather than the name of the screen. This needs no
reference to be wrong. The reference happens to agree from the other side: its
metric value is ~13 against a 20px page heading, a ratio of 0.65, where the
kit's is 1.27.

### The browser chrome pads twice

`inst-tabs--chips` carries `padding: var(--space-2)` and sits inside
`inst-toolbar`, which carries `var(--row-pad-y)`. 6 + 4 = 10px above a 24px
control, giving a **44.7px row where the reference draws 28**.

## The reference is not one system

Worth recording, because it bounds how far "match the reference" can be taken.

| | Browser pane | Usage dashboard |
|---|---|---|
| Ground | `rgb(252,252,251)` | `rgb(252,252,251)` |
| Surface | white + **1px `rgb(230,230,230)`** | `rgb(242,242,241)`, **no border** |
| Inset element | field `rgb(240,240,239)`, no border | tile `rgb(229,229,228)`, no border |

The chrome draws borders; the dashboard draws a three-tier grey stack and no
borders at all. `AUDIT-2026-08-22.md` found the same thing on the control
ladder — rungs at 20/24/30/32 with the radius ratio holding at three of them
and two stated exceptions.

Two captures of the browser pane were checked against each other and are
pixel-identical in geometry, so this is not version drift within one surface.
It is two treatments living side by side.

## Two defects found by the rebuild

**A menu item carrying both a value and a submenu splits its free space.**
`overlay.css:224` resets the mark's auto-margin for
`:has(> .inst-menu-shortcut)`, and `overlay.css:240` sets
`margin-inline-start: auto` again at equal specificity, winning on order. Two
auto margins then share the slack, so four filter rows end **46.7 / 37.3 / 8.0
/ 37.1 px** from their chevrons instead of one straight column. Holds in all
15 scale × density cells, worsening with scale (spread 38.7 at 13, 49.7 at
18). Adding `[aria-haspopup]` to the `:has` reset puts all five rows at 8.

**The status bar clips its last control.** At a 260px container its content is
304px against a 235px client width; `overflow-x` is `visible` and the panel is
`hidden`, so **69.1px of the 100.9px "Commit changes" button disappears** with
no scrollbar and no page overflow. Whole from 360px up.

## What the rebuild got right

Five of the six screens needed no new CSS. Across 15 scale × density cells and
container widths 260–720: no page overflow, no element owning a scrollbar it
should not, the status bar never going to two lines.

The menu especially. `aria-haspopup` already paints the chevron and
`aria-checked` the mark at the far edge, both from the attribute alone — the
account menu came out essentially equivalent to the reference. `menu.md:162`
still describes the old accent-and-weight rendering and lists no
`aria-haspopup`; `docscheck` passes, because it verifies classes and markup
promises rather than prose claims about rendering.
