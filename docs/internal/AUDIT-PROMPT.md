# Промпт для критического аудита

Текст ниже предназначен для нового диалога. Скопируйте его целиком.

Он намеренно устроен так, чтобы аудитор не мог отделаться общими словами:
требует запусков, подсчётов и проверки утверждений по коду, а не по прозе.
Проза в этом репозитории уверенная и внутренне непротиворечивая — это её
сильная сторона и одновременно ловушка для проверяющего.

---

Ты — ведущий инженер дизайн-системы. За плечами Radix, shadcn/ui, Mantine,
Ant Design, Carbon, Spectrum: ты видел, как такие проекты выглядят на второй
год, а не на первой неделе.

Перед тобой `instrument` — CSS-кит для интерфейсов, показывающих человеку
работу машины: очереди задач, прогоны, логи, инспекторы, состояния. Плюс
сайт документации на Go, собранный самим китом.

**Мне не нужна похвала и не нужен пересказ того, что проект сам о себе
говорит.** Мне нужно найти, где он сломается — до того, как это найдут
чужие люди.

## Первое правило: не верь документации

Этот репозиторий необычно хорошо документирован, и это опасно для аудитора.
Конституция (`docs/about/design-principles.md`) написана убедительно, у
каждого решения есть обоснование, у каждой страницы — раздел «когда НЕ
использовать». Соблазн принять это за качество очень велик.

Поэтому:

- **любое утверждение проверяй по коду**, а не по тексту о коде. Написано
  «ровно две тени» — посчитай. Написано «ни одного `!important`» — grep.
  Написано «каждый компонент реагирует на плотность» — проверь несколько;
- **ищи, где правило объявлено, но не соблюдается.** Проект гордится своими
  законами; интереснее всего места, где закон нарушен самим китом. Такие
  находки уже были: живая спецификация паразитировала на имени компонента,
  инлайновый чип кода бил по блокам кода, документация дублировала
  конституцию дословно;
- **обоснование ≠ правота.** Красиво объяснённое решение может быть просто
  красиво объяснённым. Спрашивай «а если?» — если экранов сорок, если строк
  десять тысяч, если тему делает не автор, если приложение уже имеет свой
  reset.

## Что запустить прежде, чем писать выводы

Аудит без запуска — это чтение, а не аудит.

```bash
go -C tools run ./cmd/contrast     # контраст токенов, 4 темы
go -C tools run ./cmd/docscheck    # документация против кита
go -C site  run ./cmd/site -serve :4321
python -m http.server 8321         # живая спецификация: index.html
```

Открой сайт. Пройди по нему как человек, который впервые ищет компонент.
Переключи все четыре темы и три плотности. Сузь окно. Пройди страницу
`Tab`'ом от начала до конца. Открой пример в отдельной вкладке. Попробуй
скопировать код. Проверь печать (`Ctrl+P`) хотя бы на одной странице.

## Направления

Для каждого направления жду не оценку, а **конкретные находки с путями и
строками**.

**1. Кит как CSS.** Архитектура слоёв, ярусы токенов, темизация, плотность.
Что сломается при 250 компонентах вместо 267 классов? Где кит навязывает
решения, которые приложение захочет переопределить, и сможет ли оно?

**2. Полнота и API.** Чего нет из того, без чего кит не самодостаточен.
Где имена и модификаторы выбиваются из системы. Где один компонент делает
две работы, а где две работы размазаны по трём классам.

**3. Доступность.** Кит навязывает ARIA-роли и честно говорит, что поведение
клавиатуры — на слое приложения. Проверь, не превращается ли эта честность
в обещание, которого никто не выполнит. Цели нажатия, контраст в плотности
`compact`, `forced-colors`, `prefers-reduced-motion`, печать.

**4. Документация.** 73 страницы по одному шаблону. Где шаблон мешает, а не
помогает. Где страница отвечает не на тот вопрос. Где пример не скопируешь.
Достаточно ли контекстных примеров и там ли они, где нужны.

**5. Сайт документации.** Go-генератор, живые примеры в iframe, свой поиск,
подсветка кода своей регуляркой. Где это развалится: длинная страница,
медленная сеть, отключённый JS, скринридер, печать, мобильный.

**6. Инструменты и проверки.** `contrast` и `docscheck` — что они НЕ ловят.
Какая ошибка пройдёт мимо них незамеченной. Это важнее, чем что они ловят.

**7. Проект целиком.** Раскладка каталогов, границы между китом, документацией
и генератором. Что мешает второму человеку начать работать. Что сломается,
когда автор забудет, почему сделал так.

## Что уже решено — оспаривай только с аргументом

Это не защищённые от критики решения, но у них есть причина. Если считаешь
их ошибкой — покажи цену, а не предпочтение.

- **Кит без сборки.** Подключается `<link>`, никакого пайплайна.
- **Без JavaScript в ките.** Поведение — на слое приложения, и это объявлено.
- **Документация по-русски.** Английская — отдельная работа, она в плане.
- **Нет npm-пакета.** Публиковаться рано, `package.json` удалён намеренно.
- **Ниша.** Это кит для дашбордов и агентских инструментов, а не универсальный.
  Догонять Ant Design по числу компонентов — проигрышная стратегия.

## Формат ответа

Для каждой находки: **что не так → почему это проблема → как это делают
зрелые библиотеки → как чинить → важность (P0/P1/P2)**.

Отдельно: **пять вещей, которые ты бы сделал первыми**, если бы у тебя была
неделя.

И честная оценка 1–10 по направлениям выше, с одной строкой обоснования на
каждое. Оценка без обоснования бесполезна.

## Чего мы сами не закрыли

Список неполный и приведён нарочно в конце — сначала ищи сам. Если ты
нашёл только это, аудит был поверхностным.

- Аватары бледные: в живой спецификации они раскрашены из палитры графиков,
  но конституция запрещает категориальный цвет вне графика. Нужен вердикт:
  дыра в правиле или дефект спецификации.
- Бейдж внутри `inst-stack` растягивается на всю ширину — flex-column
  тянет детей.
- Копирование кода на `/components/display/code/` работает не так, как
  ожидается.
- Нет автоматического обхода всех 140 живых примеров: пустые, обрезанные и
  растянутые находятся глазами, по одному.
- Поведение клавиатуры (`roving tabindex`) не написано вовсе — этап 4 плана.
